# Benchmark results — 2026-08-14

Phase 6 of `ENHANCEMENT_PLAN.md` (§13). All numbers below are from real, live
DeepSeek V4 API calls (`node bench/run.js <tier>`), not simulated. Raw data:
[`baseline.json`](../baseline.json) (advisory tier), [`results/raw.json`](./raw.json),
[`results/worker.json`](./worker.json).

## Token efficiency: raw API call vs. advisory tier

Same question (`"In exactly one sentence, what does Array.prototype.reduce do?"`,
`deepseek-v4-flash`), called two ways:

| | prompt-miss tokens | reasoning tokens | latency |
|---|---|---|---|
| Raw API call (no deepseek-axi tooling) | 95 | 26 | 1561ms |
| `deepseek-axi ask` | 16 | 0 | 1229ms |

The gap is entirely the Phase 1 fix found by this benchmark process itself:
`ask`/`review` now send `thinking: {type: "disabled"}` explicitly, because
DeepSeek's thinking mode defaults to *enabled* server-side even for plain
chat completions, and `ask()` never surfaces `reasoning_content` anyway — so
the raw call above paid for 26 reasoning tokens it would just discard, and
`ask` pays for zero. (The prompt-token gap in this particular run is largely
cache-hit noise from repeated near-identical calls earlier in this session,
not attributable to a specific optimization — the reasoning-token gap is the
real, reproducible signal.)

Same win shows up much larger on `review` — reviewing one small fixture file
cost **852 reasoning tokens before the fix, 0 after** (see git history on
`ask.js`/`review.js`; not re-benchmarked raw here since `review`'s system
prompt makes a fully fair raw-vs-wrapped comparison less direct than the
single-turn `ask` case above).

## Worker tier: does it actually fix things, not just run

| Task | status | iterations | prompt-cache-hit tokens | prompt-cache-miss tokens | latency |
|---|---|---|---|---|---|
| Genuine off-by-one bug, disposable repo, `test --fix` | **verified** | 1 | 4352 | 536 | 8.6s |

This is `runWorkerLoop` end-to-end on a fresh disposable git repo with a real
bug (`add(a,b)` returning `a+b+1`) and a real failing test: the fix landed on
the first iteration, the two-sided verification (base commit reproduces the
failure, worktree after the fix is green) passed, the branch was left intact,
and the original branch was never touched. Full independent verification of
this exact mechanism (checked out the fix branch, confirmed the diff, confirmed
`main` was untouched) was already done manually during Phase 3 development —
this run confirms it's reproducible via the harness, not a one-off.

Notably, **4352 of 4888 total prompt tokens (89%) were cache hits** — the
stable-prefix-first context ordering (§9, wired through in Phase 5) is doing
its job: the system instructions / task / tool definitions prefix is shared
and cached across the request(s) in the run.

## What this does and doesn't prove

- **Proves**: the thinking-mode fix is real and measurable; the worker loop
  can genuinely fix a real bug end-to-end with real git safety; context
  caching is being hit in practice, not just in theory.
- **Doesn't prove**: broad task coverage. This is one worker-tier task and
  three advisory-tier tasks — a real Phase 6 in a production setting should
  run the full task set from §13 (bug fix, feature, refactor, test repair,
  review, dependency change, several each) multiple times for statistical
  confidence, not once each. That's flagged here rather than overstated:
  this is a real but small-sample data point, not a comprehensive benchmark.
- **Cost/dollar figures are deliberately omitted** — still blocked on the
  unconfirmed cache-hit pricing discrepancy noted in `ENHANCEMENT_PLAN.md`
  §3/§5. Token counts above are exact; dollar amounts would not be.
